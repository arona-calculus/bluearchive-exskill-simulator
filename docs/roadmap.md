# 今後の開発方針: 推論用ライブラリ化

## ゴール

「TLにおける制約条件」（コスト予算、ターン数/時間制限、ゲージ条件、対象指定の制約、
ダメージ閾値など）を入力として、それを満たす**操作列**（いつ誰のEXを誰に使うか）や
**初期スキル配置**（初期編成・初期手札構成）を出力する推論用ライブラリへ育てる。

探索（制約の解釈・TL候補の選定・検証）はLLMエージェントが担い、`ba_exsim` はゲーム内実装を
コード化した**オラクル**として、LLMをゲーム内の文脈に縛り付けるガードレールとして機能する、
という役割分担を基本方針とする。利用者は開発者本人と複数人を想定し、LLMとの接続にはMCPを使う
（[architecture.md](architecture.md) の「MCPサーバー」参照）。

## 役割分担: なぜオラクルと探索を分離するか

`ba_exsim` の `CharacterSpec` フックは意図的に手続き的（Pythonの分岐処理）に
実装されている（[architecture.md](architecture.md)）。リオの自己書き換えや
水着ハナコの割り込みドローのように、生徒固有の複雑な副作用を柔軟に表現できるのは
この設計のおかげであり、今後生徒を追加していく上でも維持したい性質である。

この手続き的ロジックを丸ごと宣言的な制約（CP-SAT/SMTなど）へ翻訳しようとすると、
生徒を1体追加するたびに「手続きロジック」と「制約表現」を二重に実装する必要が生じ、
両者が食い違うリスク（バグの温床）を抱え込む。

したがって:

- **`GameEngine.play_card` を唯一の正（ground truth）とする。** 「ある局面であるアクションを
  取ったら何が起きるか」は常にこの関数に問い合わせる。
- **探索はLLMエージェントが行い、exsimは探索アルゴリズムを持たない。** 多少複雑な時間制約問題程度なら
  LLMに解かせてよい、という前提に立つ。
- exsimがガードレールとして担うのは次の4点:
  - **合法手の限定**: 手札に無い生徒は使えない、対象指定のルール等を守らせ、探索範囲を実際に起こりうる手に絞る
  - **状態の肩代わり**: 手札サイクル・ゲージ・リオのコピー等をLLMに暗算させず、常にexsimの状態を正とする
  - **早期の打ち切り**: 破綻した手順はその地点と手札状況を即座に返し、無理な枝をそれ以上伸ばさせない
  - **検証の根拠**: LLMの「制約を満たしている」という判断を機械的な判定で裏付ける
- ツールは「1手ずつ」ではなく「候補TL全体を投げて診断を受け取る」粒度にし、返り値は
  LLMが次の候補を決めやすい診断情報（どのステップで何が足りないか）を厚めにする。
- 中核ロジックはMCPに依存させず、MCPは薄いアダプタに留める（他の接続方式への乗り換えを安くするため）。

## ロードマップ

### 0. ラフTLの取り込み（実装済み）
MCPツール `list_characters` / `simulate_tl` / `find_initial_orders`。LLMがラフなTLを手順列に直し、
exsimで実行して webui の共有リンクとして返す。

### 1. 制約スキーマの定義
「TL制約」をデータとして表現する形式を先に固める（JSON/dataclass等）。想定する要素:
- 特定ステップまでの最低ゲージ/チャージ条件
- コスト予算の充足（生徒別コスト・累計消費コストは `CharacterSpec.get_cost` /
  `character_library` 経由で既に取得できる。`bluearchive-timeline-simulator/core/cost_validator.py`
  の予算チェックロジックを、この値を使う形に移植すればよい）
- 対象指定の制約（誰を対象にできる/できないか）
- 最大ターン数・最大時間
- 終端条件（`State.env` に対する述語としてのゴール状態）

このスキーマが「ライブラリ」と「LLMエージェント」の間の契約になる。

### 2. 制約チェック（`check_constraints`）
`(TL, 制約) -> (bool, 違反理由)` の形の純粋関数群を `ba_exsim` 側に用意し、MCPツールとして公開する。
LLMからも人間からも同じ基準で「このTLは制約を満たすか」を判定できるようにする。

### 3. 合法手の列挙（`legal_actions`）
`enumerate_legal_actions(state) -> list[(k, target)]` と、それぞれの手を打った結果を返すAPIを
`play_card` と並べて用意し、MCPツールとして公開する（LLMが行き詰まった時の補助）。

### 4. リモートMCP化
既存のFastAPI（`webui/backend/main.py`）に streamable-http のMCPをマウントし、認証を付けてVPSに置く。
複数人がインストールなしで（claude.ai のコネクタ等から）使えるようにする。

### 5. 実運用での調整
実際のボスの要件で LLM＋exsim のループを回し、迷走のパターン（同じ破綻を繰り返す等）を見て
ツールの返り値を調整する。

### 6. spec実装の並行拡充
実際に必要になったボスのTLを起点に、対応する生徒のspecを追加していく
（データドリブンな優先度付け）。

## 非ゴール

- exsim側に探索アルゴリズム（ビームサーチ/MCTS等）を持たせること（探索はLLMの担当）。
- `play_card` の展開をCP-SAT等の制約モデルへコンパイルする高速化レイヤー（旧ロードマップの到達目標。
  LLM主導の方針では優先度が低いため外す）。
- 任意の `CharacterSpec` を汎用的にCSP/SMTへ自動コンパイルすること
  （実装コストに対して得られる効用が小さい）。
- `ba_exsim/core/` の再設計（現状で構造的に完成していると判断）。
